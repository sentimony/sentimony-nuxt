# Initial server response time: durable cache і стабільний cache key

Дата: 2026-08-11. Гілка: `main`.

> Спека написана в автономному режимі (користувач заборонив питання).

## Питання, з якого все почалося

«Чи присутня на проді рекомендація Lighthouse *Reduce initial server response
time*?»

**Коротка відповідь: ні.** Аудит `server-response-time` проходить на всіх
перевірених типах сторінок. Але проходить він тільки тому, що замір потрапляє
в теплий edge-кеш; сам origin відповідає за 0.4–0.8 с, а Durable Cache вимкнено,
тож кожен промах edge-кешу — це повний SSR.

## Заміри (2026-08-11, prod `https://sentimony.com`)

Lighthouse 12, headless Chrome, локальний запуск.

| Прогін | Performance | `server-response-time` | LCP | Speed Index |
| --- | --- | --- | --- | --- |
| Desktop `/` | 77 | 190 мс (pass) | 2.1 с | 3.0 с |
| Mobile `/` | 94 | 280 мс (pass) | 2.1 с | 4.2 с |
| Mobile `/track/space-organ-occult-melodies?lh=cold1` | 78 | 430 мс (pass) | 3.5 с | 5.3 с |

Поріг Lighthouse для `server-response-time` — 600 мс. Найгірший замір (430 мс)
лишає запас лише 170 мс.

Тепер той самий origin без кешу. `curl`, cache-busting query, час сервера
рахується як `time_starttransfer − time_appconnect` (тобто без DNS/TCP/TLS):

| Ресурс | Час origin |
| --- | --- |
| `/` | 503–585 мс |
| `/releases` | 462–586 мс |
| `/artists` | 457–627 мс |
| `/release/va-fantazma` | 384–799 мс |
| `/track/space-organ-occult-melodies` | 392–540 мс (один прогін — 1.67 с) |
| `/api/releases` | 602–643 мс |
| `/api/tracks` | 601–677 мс |
| `/api/artists` (10 КБ) | 416–470 мс |
| `/api/release/va-fantazma` (6 КБ) | 533–551 мс |

Показовий рядок — `/api/artists`: 10 КБ відповіді за 416–470 мс. Це не обсяг
даних, це фіксована вартість «інвокація функції + раунд-тріп до Supabase».
Зменшити її кодом майже неможливо; єдиний важіль — не ходити на origin.

## Що показали заголовки

```
cache-status: "Netlify Durable"; fwd=bypass
cache-status: "Netlify Edge"; hit; ttl=3596
cdn-cache-control: public, max-age=3600, stale-while-revalidate=86400
netlify-vary: query
```

Дві знахідки.

**1. `Netlify Durable; fwd=bypass` — durable-кеш вимкнено.** Netlify має два
шари: per-PoP edge-кеш і центральний Durable Cache. Другий вмикається директивою
`durable` у `Netlify-CDN-Cache-Control`; без неї кожен PoP, який ще не бачив
сторінку, б'є в origin окремо. Тобто «холодних» відповідей рівно стільки, скільки
PoP × сторінок, а не одна на сторінку. `server/utils/cachePolicy.ts` і
`server/utils/htmlCachePolicy.ts` директиву не ставлять — це недогляд минулої
ітерації HTML-кешування, а не свідоме рішення.

**2. `netlify-vary: query` — повний query string у cache key.** Це дефолт для
serverless-відповідей. Наслідок: `sentimony.com/?utm_source=facebook` і
`sentimony.com/?fbclid=…` — окремі cache-об'єкти. Кожен перехід з реклами, розсилки
чи соцмережі, тобто рівно та аудиторія, задля якої вимірюється перше завантаження,
гарантовано отримує холодний SSR на 0.5–0.8 с. Жодна сторінка застосунку query-
параметрів не читає (перевірено `grep` по `app/` — жодного `route.query`), тож
варіація не дає нічого, а коштує кеш-міс на кожному кампанійному лінку.

## Рішення

Дві зміни, обидві в заголовках, без нових залежностей і без змін у рендерингу.

### 1. Увімкнути Durable Cache для публічних відповідей

Додати `durable` у `Netlify-CDN-Cache-Control` для публічного HTML і публічних
catalog/counter API. Стандартний `CDN-Cache-Control` лишається без `durable`:
директива Netlify-специфічна, і мета цього дублювання заголовків — залишатися
переносимими на інший CDN (див. `docs/initiatives/cloudflare-domain.md`), а не
транслювати вендорні розширення.

`private, no-store` маршрути (likes, profile, `/api/track-plays`) не чіпаємо.

### 2. Прибрати query-параметри з cache key для HTML

Віддавати `Netlify-Vary: query=_` на тих самих HTML-відповідях, які вже
кешуються. За семантикою Netlify всі «не-збіги» зі списком складаються в один
cache-об'єкт, тож allowlist з одного ніде не вживаного імені означає «усі URL з
однаковим шляхом ділять один запис». Порожній `query=` дав би те саме, але
відсутній у документованій граматиці, тому беремо явний варіант.

Обсяг навмисно обмежений HTML: до `/api/*` рекламні мітки не долітають, а
розширення варіації на API — це ризик без виграшу.

### Чого свідомо не робимо

- **Nitro cache storage на Netlify Blobs.** `defineCachedEventHandler` тримає
  кеш у пам'яті інстансу функції, тож між інвокаціями він майже не працює.
  Перенесення на Blobs прибрало б Supabase-раунд-тріпи з холодного SSR, але
  потребує нової залежності `@netlify/blobs` і не перевіряється локально. Після
  ввімкнення durable-кешу частка холодних SSR падає на порядок, і цінність цього
  кроку разом з нею; повертатися варто тільки якщо заміри після фази 1 покажуть,
  що origin усе ще на критичному шляху.
- **Перенесення регіону функцій ближче до Supabase.** Це інфраструктурне рішення
  рівня акаунта, а не репозиторію.
- **LCP/Speed Index/зображення.** У замірах вище це набагато більший борг
  (827 КБ на next-gen формати, 774 КБ на розміри), але це інша ініціатива —
  [`mobile-performance`](../../initiatives/mobile-performance.md).

## Ризики

- **Логінований користувач і закешований HTML.** Middleware не додає cache-
  заголовки, коли є Supabase-cookie, але lookup у кеші відбувається до origin,
  тож логінований відвідувач і далі може отримати анонімну сторінку. Поведінка
  не нова і не змінюється цією зміною: auth-стан гідратується на клієнті.
- **Майбутня сторінка з query-параметрами** (напр. пагінація або пошук) мовчки
  отримає чужу відповідь з кешу. Прив'язуємо це до тесту з явним поясненням,
  щоб зміна вимагала свідомого редагування allowlist.
- **Довший «хвіст» застарілого контенту.** Durable Cache зберігає відповідь
  централізовано, тож після sync каталогу стара версія живе до кінця
  `max-age`/SWR так само, як і зараз, але однаково для всіх PoP. TTL не
  змінюємо, тож вікно те саме — 1 год + 24 год SWR.

## Критерії завершення

- `cache-status` на публічному HTML показує `"Netlify Durable"` з `hit`/`stored`
  замість `fwd=bypass`.
- `sentimony.com/?utm_source=test` віддає `cache-status: "Netlify Edge"; hit`
  замість промаху.
- Origin-заміри тими самими командами: частка холодних відповідей падає;
  абсолютний час origin не регресує.
- `npm run test:unit`, `npm run typecheck`, `npm run docs:check` зелені.
