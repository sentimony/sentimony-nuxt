# Шаблон ADR

Застосовуй [політику ADR](../policy.md) й канонічне місце документації проєкту.
Скопіюй лише потрібний блок мовою проєкту. Назва, статус, фактична дата
запису, контекст, рішення та причина обов'язкові; достатньо одного абзацу.
Прибери необов'язкові поля, якщо вони не потрібні для розуміння компромісу.

## Нове рішення

```md
# <Коротка назва рішення>

Статус: proposed
Дата запису: <фактична YYYY-MM-DD>

<Контекст: що змусило обирати. Рішення: що пропонується. Причина:
чому цей варіант відповідає обмеженням і який компроміс ми приймаємо.>

Погодження: <ще очікується; після явного погодження власника зазначити
хто, коли та джерело й лише тоді змінити статус на accepted>
```

Статуси: `proposed`, `accepted`, `deprecated`, `superseded`. Для
`superseded` обов'язково вкажи посилання на заміну. Для нового рішення
збереження запису не дозволяє реалізацію, push, merge чи реліз.

Для окремого файла використовуй стабільне ім'я `NNNN-short-title.md`.
Перечитай наявні записи, обери наступний вільний номер після найбільшого
і повторно перевір його перед створенням. Створюй виключно новий файл
(наприклад, `open(path, "x")` у Python), з єдиним автором або блокуванням
на час вибору номера й створення. За колізії перечитай номери й повтори
з новим. Не перезаписуй чужий файл і не перенумеровуй старі записи.
Теку `docs/adr/` створюй лише для першого справжнього ADR, якщо саме це
місце визначено проєктом.

## Додаткові поля за потреби

1. Ретроспективність: так; джерела підтвердження; окрема відома дата
   історичного рішення. Дата запису завжди фактична, навіть для давнього вибору.
2. Розглянуті варіанти й наслідки, що пояснюють справжній компроміс.
3. Замінює: посилання на попередній запис. Після явного погодження нової
   заміни старий зберігається зі статусом `superseded` і зворотним посиланням.
   До погодження нового старий залишається чинним.
4. Причина скасування й джерело рішення власника для `deprecated` без заміни.

## Сумісність із чинним журналом

Збережи чинні ідентифікатори, порядок і еквівалентні поля наявного журналу.
Мінімальні поля можна вмістити в його формат:

```md
## <фактична дата запису YYYY-MM-DD> - <Назва>

**Рішення.** <Контекст і запропонований або погоджений вибір.>

**Чому.** <Причина; прямо познач невідоме.>

**Статус.** proposed. <Джерело явного погодження після його отримання;
ретроспективність і джерела, якщо це історичний запис; окрема історична
дата лише якщо відома; посилання на попередній запис або заміну за потреби.>
```

Зберігай еквівалентні статуси чинного журналу; у нових записах явно розрізняй
пропозицію, погодження, скасування й заміну. Старий текст не переписуй;
під час заміни доповни статус і посилання в обох записах.

## Навчальний приклад 1: історичне погодження підтверджено

Увесь контекст нижче вигаданий: обсерваторія «Паперовий Місяць», її
власниця, протокол і технічне рішення. Наведене джерело є навчальним
позначенням, його немає в репозиторії. Приклад залишається лише в шаблоні
й не додається до справжніх ADR або журналів продуктів.

```md
# Єдиний каталог зоряних листівок

Статус: accepted
Дата запису: 2026-11-01
Ретроспективність: так
Дата історичного рішення: 2025-04-12
Джерело підтвердження: вигаданий протокол PM-7 від 2025-04-12, пункт 2;
власниця вигаданої обсерваторії Марта явно погодила спільний каталог
замість окремого каталогу кожного купола та наведену нижче причину.

Куполи обмінюються зоряними листівками, і перенесення їхніх сталих
ідентифікаторів між каталогами коштовне. Власниця обрала єдиний каталог,
щоб листівка зберігала той самий ідентифікатор у всіх куполах. Компроміс:
куполи залежать від доступності спільного каталогу. Повторне ухвалення
для цього ретроспективного запису не потрібне: протокол підтверджує згоду.
```

Фактична дата створення цього навчального запису - 2026-11-01;
2025-04-12 є вигаданою датою історичного рішення, окремою від дати запису.

## Навчальний приклад 2: первісна причина невідома

Увесь контекст нижче вигаданий: музей «Скляний Вітер», схема та результати
пошуку. Це навчальна демонстрація невизначеності, яка залишається лише
в шаблоні. Вона не є рішенням реального проєкту.

```md
# Зберегти спільний архів маршрутів повітряних зміїв

Статус: proposed
Дата запису: 2026-11-01
Ретроспективність: так; описуємо виявлений стан, погодження не встановлено
Джерело фактів: вигадана схема MZ-4 містить спільний архів;
у переглянутих вигаданих документах і комітах погодження не знайдено.

Маршрути зміїв уже мають ідентифікатори в спільному архіві; його розділення
потребуватиме міграції посилань. Первісна причина невідома. Дата історичного
рішення невідома, доказу згоди власника немає. Агент пропонує сьогодні
зберегти спільний архів через ціну міграції, прийнявши спільний цикл оновлень.
Це поточна рекомендація агента; вона не підтверджує історичну мотивацію.
Погодження власника ще очікується.
```

Фактична дата створення цього навчального запису - 2026-11-01. Власник
може залишити питання відкритим. Якщо він явно погодить рекомендацію,
зафіксуй її як нове рішення з датою сьогоднішнього ухвалення та джерелом
погодження; невідоме минуле так і лишається невідомим. Сам стан коду
не робить запис `accepted`. Якщо окремо знайдено доказ історичного
погодження без причини, історичний `accepted` допустимий з посиланням
на цей доказ і прямою позначкою невідомої причини.
